# Local data contract — 2026-10-27

`src/storage/repository.ts` owns schema version 1: locale (`bg`/`en`), onboarding flag, ingredients, recipes, pricing profile and immutable historical recipe snapshots. All monetary/quantity values are decimal strings. Domain contracts live in `src/domain/index.ts`; JSON is structurally validated before costing. Dates for mutations/history are ISO timestamps; the VAT profile effective date is a calendar date.

The repository exposes `createDemoState`, `loadState`, `saveState`, `readRecoveryBackup`, `changePrice`, `saveRecipe`, `saveProfile` and `validateState`. Optional `StorageLike` parameters on load/save/recovery support integration tests without a browser. The synchronous browser adapter uses `micromargin.state.v1`; there is no hosted database, authentication, cloud sync or tenant isolation in this demo. Separate browser profiles are needed on shared devices.

Pack-price changes create an immutable history record and snapshots before and after every dependent recipe. Recipe saves increment the existing version and snapshot both versions; new recipes start at version 1. Profile changes snapshot every recipe under both assumption sets. Snapshot inputs, profile, recipe and calculated totals are copied, and totals are checked against their historical inputs on load. Current edits never rewrite prior snapshot values. No history is silently pruned.

Boundary checks include known schema/locale/basis/unit/yield enums, bounded strings, decimal strings, booleans, positive safe-integer recipe versions, bounded arrays, unique ingredient/recipe IDs, chronological ingredient history, matching current/history price, valid ingredient references and unit-compatible domain calculations. Limits: 500 ingredients, 200 recipes, 250 lines per recipe, 2,000 prices per ingredient, 2,000 snapshots, and 4 MiB of UTF-8 serialized JSON. A limit failure preserves existing stored state and surfaces an export/recovery message. These bounds suit the 5–40 product local demo; a database history model is required for longer operation.

Corrupt/unsupported stored data is retained in its original key until its exact raw text has been copied and verified at `micromargin.state.v1.recovery`. A synthetic demo may then replace the active state, with an explicit warning. An existing different recovery backup is never overwritten; inability to preserve the original blocks saves. `readRecoveryBackup()` returns the exact original recovery text (or `null` when absent) for a separate Settings download. It never parses, renders, executes or deletes that untrusted text; a storage read failure throws a descriptive error. The normal Settings export contains current state only. Recovery text also remains available through browser developer tools (`localStorage.getItem('micromargin.state.v1.recovery')`). Storage unavailable/quota errors are shown, and in-memory changes can be exported. This is one-browser durability, not a backup guarantee or concurrency solution.

## PostgreSQL/Supabase boundary before real use

Create businesses/tenants, memberships, ingredient packs, immutable price revisions, recipe revisions/lines, pricing-profile revisions and cost snapshots. Every row needs a server-owned tenant foreign key; every query/mutation must authorize membership from the authenticated session. Never accept a client-provided tenant ID as proof. Use transactionally consistent revisions and optimistic version checks; localStorage's last-writer behavior is insufficient for multiple tabs/users. Add row-level-security tests for cross-tenant read/write attempts, server validation, migration/version tests, deletion/export lifecycle, encrypted transport/storage, document object isolation and retention policy before connecting real accounts or invoices. The current repository interface anticipates that replacement; it does not implement those production controls.
